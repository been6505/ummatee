# แผนพัฒนา Ummatee ให้เป็นแอปบนมือถือ

เอกสารนี้เขียนจากสิ่งที่ **มีอยู่จริงในโค้ดตอนนี้** ไม่ใช่แผนทั่วไป
ทุกข้อจึงระบุว่าของเดิมมีอะไรแล้ว ต้องทำเพิ่มอะไร และติดข้อจำกัดอะไร

เป้าหมายที่ตั้งไว้: **ให้ผู้ใช้เข้าถึงง่าย และรับรู้ข่าวสาร/การอัปเดตการช่วยเหลือได้ง่ายขึ้น**

---

## สรุปสั้นที่สุด

เว็บนี้**เป็นแอปติดตั้งได้อยู่แล้ว** ตั้งแต่ก่อนเริ่มแผนนี้ — ไม่ต้องเขียนใหม่ ไม่ต้องแปลงเป็น React Native

สิ่งที่ขาดจริง ๆ มีสองอย่าง:

1. **ไม่มีใครรู้ว่าติดตั้งได้** → แก้แล้วใน `InstallAppBanner.jsx` (คอมมิต `37b72f9`)
2. **ไม่มีการแจ้งเตือน** → ยังไม่มี ต้องตัดสินใจเรื่องค่าใช้จ่ายก่อน (ดูเฟส 2)

ข้อ 2 คือหัวใจของ "รับรู้ข่าวสารได้ง่ายขึ้น" ที่เหลือเป็นส่วนขยาย

---

## ของเดิมที่มีอยู่แล้ว (ไม่ต้องทำซ้ำ)

| สิ่งที่ต้องมีเพื่อเป็นแอป | สถานะ | อยู่ที่ไหน |
|---|---|---|
| Web app manifest | ✅ มี | `vite.config.js` → `VitePWA({manifest})` |
| ไอคอน 192 / 512 / maskable | ✅ มี | `public/icon-192.png`, `icon-512-maskable.png` |
| Service worker + ทำงานออฟไลน์บางส่วน | ✅ มี | `vite-plugin-pwa`, `registerType:'autoUpdate'` |
| เปิดเต็มจอไม่มีแถบ URL | ✅ มี | `display:'standalone'` |
| แยกแอปแอดมินออกจากแอปผู้ใช้ | ✅ มี | `admin-manifest.webmanifest` + สลับ `<link rel=manifest>` ใน `App.jsx` |
| ปุ่มติดตั้งฝั่งแอดมิน | ✅ มี | `InstallAdminApp.jsx` |
| **ปุ่มติดตั้งฝั่งผู้ใช้** | ✅ เพิ่งเพิ่ม | `InstallAppBanner.jsx` |
| กู้คืนเมื่อ chunk เก่าค้างหลัง deploy | ✅ มี | `lazyWithReload()` ใน `App.jsx` |
| **การแจ้งเตือน (push)** | ❌ **ยังไม่มี** | — |
| **ตัวตนผู้ใช้ทั่วไป** | ❌ **ยังไม่มี** | ลูกค้าซื้อแบบ guest ไม่มีบัญชี |
| อยู่บน App Store / Play Store | ❌ ยังไม่มี | — |

**ข้อสรุป:** ระยะทางจาก "เว็บ" ไป "แอป" สั้นกว่าที่คิดมาก งานที่เหลือเกือบทั้งหมดคือ *การแจ้งเตือน* ไม่ใช่ตัวแอป

## เฟส 1 — ให้คนติดตั้งได้จริง ✅ ทำแล้ว

`InstallAppBanner.jsx` + `utils/installPrompt.js`

- Android/Chrome ติดตั้งจบในปุ่มเดียว (ดัก `beforeinstallprompt`)
- iOS Safari ยิง event นี้ไม่ได้เลย → แสดงขั้นตอน "เพิ่มไปยังหน้าจอโฮม" แทน
  พร้อมย้ำว่า**ต้องเปิดใน Safari เท่านั้น** (เปิดใน Chrome บน iPhone จะไม่มีเมนูนี้ — คนติดตรงนี้กันมากที่สุด)
- ปิดแล้วเงียบ 30 วัน / ติดตั้งแล้วไม่ถามอีก
- ไม่ขึ้นบนหน้าเช็คเอาท์ (ห้ามมีอะไรบังปุ่มยืนยันคำสั่งซื้อ)

### สิ่งที่ควรวัดผลก่อนไปเฟสถัดไป

ยังไม่มีตัวนับว่ามีคนติดตั้งจริงกี่คน แนะนำให้เพิ่มก่อน เพราะมันตัดสินใจแทนเราได้ว่าเฟส 2 คุ้มไหม:

```js
// ตอน appinstalled — เขียนลง stats/site เหมือนตัวนับผู้เข้าชมที่มีอยู่แล้วใน App.jsx
setDoc(doc(db,'stats','site'), { installs: increment(1) }, { merge:true })
```

## เฟส 2 — การแจ้งเตือน (จุดตัดสินใจสำคัญที่สุด)

นี่คือส่วนที่ทำให้ "รับรู้ข่าวสารได้ง่ายขึ้น" เป็นจริง — และเป็นส่วนเดียวที่**มีค่าใช้จ่ายเข้ามาเกี่ยว**

### ข้อจำกัดที่ต้องรู้ก่อนตัดสินใจ

1. **การ *รับ* แจ้งเตือนฟรี** — FCM ฝั่ง client ไม่มีค่าใช้จ่าย
2. **การ *ส่ง* ต้องมีเซิร์ฟเวอร์** — FCM HTTP v1 ต้องเซ็น JWT ด้วย service account
   ซึ่ง**ห้ามเอาไว้ในโค้ดฝั่งเว็บเด็ดขาด** (ใครก็เปิดดูได้ = ส่งแจ้งเตือนปลอมหาผู้ใช้ทุกคนได้)
3. **โปรเจกต์นี้อยู่แผน Spark** — deploy Cloud Functions ไม่ได้ (เคยลองแล้ว ติด Artifact Registry / Secret Manager)
4. **iOS รองรับ web push ตั้งแต่ 16.4** แต่**เฉพาะเมื่อผู้ใช้กด "เพิ่มไปยังหน้าจอโฮม" แล้วเท่านั้น**
   → เฟส 1 ไม่ใช่แค่ของแถม มันคือ**เงื่อนไขบังคับ**ของเฟส 2 บน iPhone

### ทางเลือกการส่ง — เรียงตามความเหมาะกับโปรเจกต์นี้

| ทาง | ค่าใช้จ่าย | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **A. Google Apps Script เป็นตัวส่ง** | **ฟรี** | ทีมนี้**ใช้ Apps Script อยู่แล้ว** (`docs/volunteer-apps-script`, `sheets-export-apps-script`) — คุ้นมือ, เก็บ service account ใน Script Properties ได้ปลอดภัย | ส่งช้ากว่า, โควตา Apps Script จำกัด, ต้องดึงรายชื่อ token จาก Firestore ผ่าน REST |
| **B. Cloud Functions (Blaze)** | ผูกบัตร มีฟรีเครดิตต่อเดือน ปกติจ่าย ~0 บาท | ตรงไปตรงมาที่สุด, ทำ trigger อัตโนมัติได้ (มีคนบริจาค → แจ้งทีมทันที) | ต้องผูกบัตร — เป็นการตัดสินใจขององค์กร ไม่ใช่ของโค้ด |
| **C. ไม่ทำ push เลย ใช้ "ฟีดข่าว" ในแอปแทน** | ฟรี | ไม่ต้องมีเซิร์ฟเวอร์เลย, ไม่ต้องขอสิทธิ์ notification | ผู้ใช้ต้องเปิดแอปเองถึงจะเห็น — ไม่ตอบโจทย์ "รับรู้ง่ายขึ้น" เต็มที่ |

> **แนะนำ:** เริ่มที่ **C ก่อน แล้วต่อด้วย A**
> C ใช้ของที่มีอยู่แล้วทั้งหมด ทำได้ทันทีโดยไม่ต้องตัดสินใจเรื่องเงิน และ**ยังจำเป็นอยู่ดี**แม้จะทำ push ทีหลัง
> (คนที่ไม่กดอนุญาตแจ้งเตือน — ซึ่งเป็นคนส่วนใหญ่ — ต้องมีที่ให้ตามอ่าน)

### สิ่งที่ต้องเพิ่มในโค้ดถ้าทำ push (ทาง A หรือ B)

```
public/firebase-messaging-sw.js     service worker ของ FCM (คนละตัวกับ sw.js ของ workbox)
src/data/pushTokens.js              ขอสิทธิ์ + getToken() + เขียนลง Firestore
firestore.rules                     collection pushTokens:
                                      create ได้โดยไม่ต้องล็อกอิน (ผู้ใช้ทั่วไปไม่มีบัญชี)
                                      list/read ได้เฉพาะแอดมิน — token คือรายชื่อผู้ใช้ทั้งหมด
src/pages/AdminBroadcast.jsx        มีหน้าอยู่แล้ว เพิ่มปุ่ม "ส่งแจ้งเตือน" ต่อยอดได้เลย
```

⚠️ **จุดที่พลาดง่าย:** `pushTokens` ต้องเปิดให้ `create` โดยไม่ล็อกอิน (เหมือน `productReviews`)
แต่ต้อง**ปิด `list` สนิท** — ถ้าใครอ่านทั้ง collection ได้ ก็ได้จำนวนและ token ผู้ใช้ทุกคนไป
เป็นรูปแบบเดียวกับที่ใช้กับ `shopIssues` แล้ว

## เฟส 3 — ให้ "ฟีดข่าวการช่วยเหลือ" มีอยู่จริง

ตอนนี้ข่าวการช่วยเหลืออยู่กระจายตามหน้าโครงการ ไม่มีที่รวมที่เปิดแล้วเห็นทันทีว่า "ล่าสุดเกิดอะไรขึ้น"
ซึ่งเป็นสิ่งที่แอปบนมือถือต้องมี — คนเปิดแอปวันละครั้งเพื่อดู *อะไรใหม่*

**ข่าวดี: ข้อมูลมีอยู่แล้วเกือบครบ** ไม่ต้องเก็บใหม่

- `campaigns` — ความคืบหน้าแคมเปญ (มี `campaignProgress.js` คำนวณอยู่แล้ว)
- `AdminAidMap` — พื้นที่ที่ช่วยเหลือ
- `contentTemplates` / ปฏิทินคอนเทนต์ — สิ่งที่ทีมโพสต์
- `stats/site` — ยอดรวม

**สิ่งที่ต้องทำ:** หน้า `/updates` ที่รวมของพวกนี้เรียงตามเวลา + การ์ดสรุปบนหน้าแรก
เป็นงานฝั่ง UI ล้วน ไม่ต้องแตะ backend และ**ไม่ต้องรอการตัดสินใจเรื่องค่าใช้จ่าย**

---

## เฟส 4 — ขึ้น App Store / Play Store (ทำก็ได้ ไม่ทำก็ได้)

ทำ**หลังสุด** เท่านั้น เพราะไม่ได้เพิ่มความสามารถอะไรให้ผู้ใช้เลย — ได้แค่ "ค้นเจอในสโตร์"

| | Android | iOS |
|---|---|---|
| วิธี | **TWA** (Trusted Web Activity) — ห่อเว็บเดิม ไม่ต้องเขียนโค้ดใหม่ | **Capacitor** ห่อเป็น WebView |
| ค่าใช้จ่าย | $25 ครั้งเดียว | **$99 ต่อปี** |
| ความเสี่ยงถูกปฏิเสธ | ต่ำ | **สูง** — Apple ปฏิเสธแอปที่เป็นเว็บห่อเฉย ๆ (Guideline 4.2 Minimum Functionality) |

> ถ้าจะทำจริง แนะนำ **Android ก่อนอย่างเดียว** ($25 ครั้งเดียว ความเสี่ยงต่ำ)
> ส่วน iOS ให้ใช้ PWA ผ่าน "เพิ่มไปยังหน้าจอโฮม" ไปก่อน — ได้ผลเหมือนกันในสายตาผู้ใช้ และไม่มีค่ารายปี

## สิ่งที่ **ไม่ควร** ทำ

- **อย่าเขียนใหม่เป็น React Native / Flutter** — จะกลายเป็นโค้ดสองชุดที่ต้องดูแลคู่กันตลอดไป
  ทั้งที่ 62 หน้า + 52 โมดูลข้อมูลที่มีอยู่ทำงานได้ดีอยู่แล้ว และไม่มีฟีเจอร์ไหนต้องใช้ native API
- **อย่าใส่ service account key ลงในโค้ดฝั่งเว็บ** ไม่ว่ากรณีใด
- **อย่าให้แถบชวนติดตั้งเด้งทันทีที่เปิด** — เท่ากับป๊อปอัปขวางเนื้อหา (ตอนนี้หน่วง 6 วินาที)
